# 精简编辑

本文件只定义**如何处理目标文本**。编辑者接收已确认的精简方案，据此修改目标文件；不得扩大审计范围，不得写入讨论过程。

## 编辑原则

精简的目标是**保留完整命题，删除推理转录、重复和装饰**。一个命题包含：actor 与 action、条件 / 时序 / 顺序、modality（must / may / never）、否定保证与例外、ownership、副作用、失败模式与后果。

删除任何文字前，先枚举这段话包含的命题；只有每条事实子句都存活、且结果更清晰时，才算一次好的精简。更少的字数本身不是改进。

## 各类文本的处理方式

### 保留

- 当前行为、失败方式、时间性、所有权、权限和安全使用事实。
- 非显然的契约或不变量：行为、失败、ownership、调用者或维护者在现场需要的后果。
- 非显然的 rationale——省略它可能导致误用或错误简化时，保留后果并链接其归属说明。
- 搜索可用的机制名，和有意义的 modal / temporal / negative emphasis。

### 改写为当前事实

- 过程叙事："本次删除了""之前用 X 现在用 Y""reviewer 要求""先做 A 再证明 B""v1 / 这一版曾经……"——改写为当前状态，例如把回归改成现在时反事实（"没有 X 就会 Y"），而不是过往历史（"曾经会 Y"）。
- 作者会话视角：`(decision 7)`、`(audit C2)`、`design §4.7`、阶段标签、"这个 PR 加了""在前一个提交里"——若有已提交的归属来源则按名字和路径引用，否则删除引用并把其事实子句改写为独立陈述。

### 直接删除

- 没有事实负载的设计会议引用、审计编号、评审对话、草案章节、会话专用引用。
- 控制流叙述（"先 X 再 Y"）、测试走读、对显然分支的证明——只保留非显然的契约或不变量。
- 为假想消费者扩展的边界；风格偏好包装成安全要求；用大量 MUST/粗体代替可验证后果。
- 推诿式评论（"应该够用了"）、无标记的延期计划——提升为 TODO/FIXME，或改写为实际边界。

### 迁移到 owner

- 同一事实只保留一个 owner；其他位置留一行可解析链接。
- 情境化操作流程移到 skill/cookbook；设计理由移到 Agent Note；类型和运行语义移到 source/JSDoc/subsystem；根 standing instructions 只保留每次会话都需要的短规则。
- 保持条规在一到三行，加链接到其 rationale。

## 不要做的

- 不写审计编号、候选清单、删改争论或验收过程到目标文件。
- 不把风格偏好提升为安全规则，不自动把所有细节迁入 reference。
- 不制造编辑来凑一个删除目标；没有证据的删除不改。
- 不为了更短的文本而删掉真实的行为、失败、时序、所有权或安全使用事实。

## 风格要点

- 保留完整局部合同，激进链接到归属文档（架构、rationale、算法、历史、扩展示例）。一个解释只有一个 home；必要合同事实可局部重复。
- 用精确词替换含义模糊的通用词；当某条规则、API、字段、类型、校验点或失败状态能把事实说得更准时才保留术语。
- 去除形容词、重复和叙述，只有当每条事实子句都存活且结果更清晰时才删。

## 输出结构

编辑者输出编辑后的目标文件 diff，并附一张结构化的处理表：每处改动的 `target`、`classification`、`action`（保留/改写/删除/迁移）、`evidence` 和改后位置。不输出逐步思考记录。
