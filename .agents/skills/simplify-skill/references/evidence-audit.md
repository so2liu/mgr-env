# 证据审计

本文件只定义**如何判定一条约束是否真实存在**。审计者只读，不编辑。它提取目标文件中每条规则/主张，标注其判定并给出证据，输出为结构化结论，供编辑者消费。

## 审计任务

对目标文件中的每条规则或主张，回答四件事：

1. **适用范围（scope）**：这条规则约束什么行为 / 哪段代码 / 哪个调用链？边界在哪里？
2. **owner**：这条事实由谁拥有？有没有更具体的权威来源（某个文件、某段代码、某个子系统）应当持有它？
3. **证据**：有没有生产消费者、执行门禁、事故/缺陷记录或稳定 owner 能证明它？（测试、文档、Agent Note 是证据来源，但不自动成为永远保留的理由。）
4. **违反后果**：违反它会怎样？后果是可观察的失败、数据不一致、安全问题，还是纯风格偏好？

## 判定标注

每条规则标为以下一种：

- **keep**：真实约束，且当前 target 是该事实的正确 owner。
- **relocate**：真实约束，但 owner 在别处——本文件只留一行可解析链接，指向真正的 owner。
- **condense**：真实约束，但当前表述冗余，可压缩为一条短规则 + 指向详情的链接。
- **delete**：不是真实约束，或已被更权威来源完全覆盖、无独立价值。
- **needs-owner-decision**：真实存在，但归谁的处置无法从上下文确定，需用户决策。

`keep` 必须至少能回答：适用范围是什么、谁拥有事实、违反会造成什么、证据在哪里。四者缺一，不能算 `keep`。

## 如何判定“真实存在”

以下信号支持 `keep`：

- 代码、配置解析、wire/durable format、执行门禁或生产调用能直接验证。
- 由真实事故或已复现 bug 产生，且最小规则能防止同类回归。
- 明确约束安全、权限、资源所有权、取消/清理、兼容性或数据持久化。
- 每次相关任务都需要，且没有更具体的 owner 可以按需加载。
- 保留的行为可能在细节上略有不同，但新行为仍然合理且更易解释。

以下信号支持 `delete` 或 `relocate`：

- 只是目录、命令、包、测试或状态的手抄清单，已有权威来源。
- 同一规则在多个文件中多次重述——保留唯一 owner，其他位置留一行链接。
- 描述作者如何得出结论、评审如何推进、曾经怎样修改，而非 HEAD 的当前义务。
- 为假想消费者扩展边界，没有生产调用、真实故障或明确产品 owner。
- 把风格偏好包装成安全要求，或用大量 MUST/粗体替代可验证后果。

以下信号**不构成**新增限制的证据：

- “可能未来有用”“更完整”“模型也许会犯错”——这类推测不进入保留清单。
- 只因文字长或复杂就判为废话——应先找到 owner 和消费者，再判断。

"可能未来有用""更完整""模型也许会犯错" 不构成保留证据；出现真实回归后，再把最小防复发约束加入 skill 并链接其 owner。

## 特殊注意

- 安全、权限、持久化、生命周期、兼容性规则默认高风险，仍需确认它描述的是**当前机制**而非假设。若只是过去的假设，按 `needs-owner-decision` 或 `delete` 处理。
- 测试、文档或 Agent Note 是证据来源，不自动成为永远保留的理由。生产调用与当前代码优先。
- 不要为“预防假想失败”提前扩充保留清单；真实问题出现后再补最小防复发约束。

## 输出结构

审计者输出下表（每行一条）：

| target | classification | owner | evidence | risk | action |
|---|---|---|---|---|---|
| 规则/主张的描述 | keep/relocate/condense/delete/needs-owner-decision | 事实归属的文件或代码 | 支持此判定的证据位置 | 误判的风险级别 | 建议的下一步 |

只输出结构化事实与证据，不输出自由形式的思考记录或逐步推理。
